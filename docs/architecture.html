How it works, from the ground up

Two roads in, one plan out

Everything that arrives is split into two kinds of thing: asks (what the customer wants answered) and statements (what someone says is true). Asks become requirements. Statements settle questions. The planner puts the two together and says what to do next.

Where requirements come from

From three places, and only one of them needs the extract model. Then one merge call per deal turns all 184 asks into 68 requirements.

120

Questionnaire rows

Code reads them; no model. A spreadsheet already has an id and a question per row, so a model would only add risk. Example: Provide latest penetration test and remediation status. (Acme Q-008)

30

Customer emails

The extract model finds them, because an email is prose. Example from Acme's email: Complete the supplier profile. Not every ask is a question: Target an October production pilot is a deadline, and Answer for the configuration Acme would receive is an instruction for how to answer.

34

Predicted

Also from extract, but from Lantern's own guidance and Jai's notes: what customers like this usually ask next. Example: Provide a recent red-team or penetration-test report; evidence older than about six months may not work. These are marked predicted, so Jai can prepare before the customer asks.

All three of those pen test asks are the same need. The merge call puts them in one requirement, acme:Q-008 Penetration test and remediation, linked to two questions: pen_test and pen_test_remediation. Answering it once answers all three.
